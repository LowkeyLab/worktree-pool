# Publishing worktree pool

The supported product is the `worktree-pool` CLI. Its Rust library is an
implementation detail without an API compatibility guarantee. During 0.x,
compatible CLI fixes use patch releases and breaking CLI changes use minor
releases. JSON receipts, events, and catalog formats have independent version
contracts; a version bump never authorizes rewriting immutable history or
bypassing unsupported-version refusals. Minimum-support changes require review.

## Prepare a release

Use a pooled assignment for repository edits. In an ordinary PR, update
`Cargo.toml`, its `Cargo.lock` package entry, and the versioned `CHANGELOG.md`
entry. Run all `AGENTS.md` checks, including the package/minimum-Git verifier.
Merge before tagging. Initially only `vMAJOR.MINOR.PATCH` tags are accepted.

After explicit release approval, fetch `origin/main` and check out the exact
merged commit in a clean checkout. Create an annotated tag matching the manifest
version. `install/release.py` refuses dirty/untracked files, mismatched tag/version,
a tag pointing elsewhere, an unmerged commit, or a missing changelog entry.

Prepare and accept the archive, using new absolute output directories outside
any reusable checkout. Set `release_tag`, `release_evidence`, and
`release_acceptance` to the approved tag and new private directory paths:

```sh
umask 077
python3 install/release.py prepare --tag "$release_tag" --output "$release_evidence"
release_version="${release_tag#v}"
python3 install/verify.py --archive "$release_evidence/worktree-pool-$release_version.crate" --output "$release_acceptance"
```

Release preparation and upload must use the exact Rust/Cargo toolchain pinned
in `rust-toolchain.toml`, as the workflow does. A Nix development shell may supply
a newer compiler; use the pinned release toolchain for actual release evidence.

Retain `release.json`, the `.crate`, and acceptance logs/reports. The release
record binds tag, commit, version, toolchain, and archive SHA-256. The copied-source
archive generated by ordinary CI is not a substitute for this tagged archive.
Cargo packages from a manifest, not a supplied archive: clean-source reproducible
packaging is checked before upload, and the registry checksum is checked afterward.

## First publication (separate approval required)

The first upload is manual because Trusted Publishing requires an existing crate.
Do not push the first version tag until the manual upload has completed; otherwise
the workflow attempts OIDC for a crate whose publisher is not configured yet.

1. Log into crates.io as GitHub user `tacascer`, verify the account email, and
   confirm the `worktree-pool` name is still available. Stop for a naming decision
   if another owner has claimed it. No team owner is added by this setup.
2. Create a short-lived token with only the permissions needed to create/publish
   this crate. Keep it out of GitHub secrets, source, receipts, and logs. Enter it
   through `cargo login`; never put its value in a command argument.
3. Confirm explicit approval of the exact tag/commit/archive and acceptance
   evidence before upload. With new absolute `release_preflight` and
   `release_registry_evidence`, and `release_registry_acceptance` directory paths:

   ```sh
   python3 install/release.py check --tag "$release_tag" --evidence "$release_evidence" --output "$release_preflight"
   ```

   Inspect `state.json`. If `decision` is `publish`, run:

   ```sh
   cargo publish --locked --registry crates-io
   ```

   If it is `verify-existing`, skip uploading. A mismatch or service failure stops
   the procedure. Never overwrite an existing version or move its release tag.
4. Verify the uploaded checksum, then install the exact registry version and run
   the full installed public CLI/Git 2.36 acceptance in a new directory:

   ```sh
   python3 install/release.py verify-registry --evidence "$release_evidence" --output "$release_registry_evidence"
   python3 install/verify.py --archive "$release_evidence/worktree-pool-$release_version.crate" --registry-install --output "$release_registry_acceptance"
   ```

5. Revoke the temporary token on crates.io and run `cargo logout`. Verify the
   crate owner is `tacascer`, the exact version exists, and acceptance succeeded.

Account login, email verification, token creation/revocation, and crates.io
publisher configuration are maintainer actions in the service UI. The repository
cannot establish them without the owner's authenticated session.

## Configure subsequent publication

The GitHub environment `crates-io` in `LowkeyLab/worktree-pool` is configured
without required reviewers and allows only tags matching `v*`; deliberate version-tag push is approval. In the crate's
Trusted Publishing settings, configure:

- GitHub owner: `LowkeyLab`
- Repository: `worktree-pool`
- Workflow filename: `publish.yml`
- Environment: `crates-io`

After bootstrap configuration, push the approved version tag. Future releases
follow the same version/changelog PR and deliberate tag-push procedure. The
workflow runs minimum/stable checks and accepts the exact tagged archive before
publication. Only its publishing job has OIDC permission; no long-lived token is
stored. Actions are commit-pinned. Publication runs are serialized and running
uploads are not cancelled by a newer tag.

## Failed or interrupted publication

Inspect the workflow evidence and registry before retrying an uncertain upload.
An explicit registry 404 means absence; authentication, network, throttling, and
server errors stop rather than authorize another upload. A rerun reproduces the
archive from the same tag and toolchain, checks the existing checksum, skips an
already-completed matching upload, and repeats registry-installed acceptance.
A different checksum stops and preserves the package and tag.

If an upload succeeded but checksum or installed acceptance fails, the release
failed. No automatic yank, retag, or version replacement occurs. Investigate the
recorded evidence and approve a corrective release or explicit yank separately.
Keep receipts and logs even when GitHub reports a failed run.

## Validation limits

Local checks establish release guards, archive reproducibility, and installed
CLI behavior. The initial setup does not upload version 0.1.0. OIDC exchange and
installation from crates.io can only be established after bootstrap publication
and publisher configuration; do not describe these as verified beforehand.
